• For a backend-only container handling 50,000+ hosts per scan, here is a practical starting point.

  Recommended K8s resources
  ─────────────────────────

  resources:
    requests:
      cpu: "1000m"      # 1 vCPU
      memory: "1Gi"
    limits:
      cpu: "2000m"      # 2 vCPU
      memory: "2Gi"

  Why these numbers?
  ──────────────────

  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────────┐
  │ Factor                                   │ Estimate                                             │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────────┤
  │ Go binary + runtime idle                 │ ~50–80 MB                                            │
  │ One 50k-host callback envelope in memory │ ~300–600 MB (depends on passwd_file/group_file size) │
  │ 10 worker goroutines + async comparisons │ ~50–150 MB                                           │
  │ GC headroom during heavy ingestion       │ ~300–500 MB                                          │
  │ Peak working set                         │ ~0.8–1.3 GB                                          │
  │ CPU during envelope ingestion            │ 1–1.5 cores (JSON parsing + DB writes + comparisons) │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────────┘

  So 1 Gi request / 2 Gi limit gives enough headroom for a 50k-host burst without OOMKilling, and 2 vCPU limit covers the ingestion spike.

  Probes
  ──────

  Use the existing health endpoint:

  livenessProbe:
    httpGet:
      path: /api/health
      port: 8080
    initialDelaySeconds: 10
    periodSeconds: 10
  readinessProbe:
    httpGet:
      path: /api/health
      port: 8080
    initialDelaySeconds: 5
    periodSeconds: 5

  Scaling
  ───────

  A single envelope is processed by one pod (the handler keeps the full hosts array in memory and fans out 10 workers), so adding replicas does not speed up one callback. It does help with:

  • Concurrent UI/API requests
  • High availability
  • Multiple smaller callbacks arriving at the same time
  Suggested HPA:

  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        targetAverageUtilization: 70
    - type: Resource
      resource:
        name: memory
        targetAverageUtilization: 80

  If you want to run a single pod to save cost, keep the 2 Gi limit — that is the important part for 50k-host scans.

  Tuning knobs to keep memory under control
  ─────────────────────────────────────────

  You can pass these via env vars in the Deployment:

  env:
    - name: GOGC
      value: "50"          # more aggressive GC during ingestion
    - name: GOMEMLIMIT
      value: "1500MiB"     # soft memory target for the Go runtime

  GOMEMLIMIT is especially useful: it tells Go to pace GC so RSS stays closer to 1.5 Gi instead of spiking toward the 2 Gi limit.

  If you also add the frontend to the same container
  ──────────────────────────────────────────────────

  Add roughly:

  resources:
    requests:
      cpu: "50m"
      memory: "64Mi"
    limits:
      cpu: "200m"
      memory: "128Mi"

  But the recommended setup is separate frontend + backend pods.

  What to watch in production
  ───────────────────────────

  • container_memory_working_set_bytes vs limit
  • CPU spikes during callback ingestion
  • DB connection pool usage (MAXOPENCONNS defaults to 100)
  • Callback response time from AAP (the envelope is accepted quickly, but processing continues in the background)
  Bottom line
  ───────────

  Start with:

  requests: cpu 1000m, memory 1Gi
  limits:   cpu 2000m, memory 2Gi

  Monitor after a few real 50k-host scans. If peak RSS stays well under 1.5 Gi, you can lower the limit to 1.5 Gi. If you see OOMs, raise it to 3 Gi or reduce per-host payload size first.

  Scaling
  ───────

  A single envelope is processed by one pod (the handler keeps the full hosts array in memory and fans out 10 workers), so adding replicas does not speed up one callback. It does help with:

  • Concurrent UI/API requests
  • High availability
  • Multiple smaller callbacks arriving at the same time
  Suggested HPA:

  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        targetAverageUtilization: 70
    - type: Resource
      resource:
        name: memory
        targetAverageUtilization: 80

  If you want to run a single pod to save cost, keep the 2 Gi limit — that is the important part for 50k-host scans.

  Tuning knobs to keep memory under control
  ─────────────────────────────────────────

  You can pass these via env vars in the Deployment:

  env:
    - name: GOGC
      value: "50"          # more aggressive GC during ingestion
    - name: GOMEMLIMIT
      value: "1500MiB"     # soft memory target for the Go runtime

  GOMEMLIMIT is especially useful: it tells Go to pace GC so RSS stays closer to 1.5 Gi instead of spiking toward the 2 Gi limit.

  If you also add the frontend to the same container
  ──────────────────────────────────────────────────

  Add roughly:

  resources:
    requests:
      cpu: "50m"
      memory: "64Mi"
    limits:
      cpu: "200m"
      memory: "128Mi"

  But the recommended setup is separate frontend + backend pods.

  What to watch in production
  ───────────────────────────

  • container_memory_working_set_bytes vs limit
  • CPU spikes during callback ingestion
  • DB connection pool usage (MAXOPENCONNS defaults to 100)
  • Callback response time from AAP (the envelope is accepted quickly, but processing continues in the background)
  Bottom line
  ───────────

  Start with:

  requests: cpu 1000m, memory 1Gi
  limits:   cpu 2000m, memory 2Gi

  Monitor after a few real 50k-host scans. If peak RSS stays well under 1.5 Gi, you can lower the limit to 1.5 Gi. If you see OOMs, raise it to 3 Gi or reduce per-host payload size first.

• Exactly — that changes the shape of the spike but not the peak size. You get one big HTTP request that contains all 50,000 hosts, and the backend then fans that out to 10 workers.

  Here is the more precise sizing for that pattern.

  Memory: the envelope dominates
  ──────────────────────────────

  The whole JSON body is unmarshalled into memory once and stays there until the last worker finishes.

  Quick formula:

  peak RSS ≈ 200 MB (Go runtime + binary)
              + (N_hosts × avg_payload_size × 2–4x overhead)

  ┌──────────────────┬────────────────┬────────────────┬─────────────┐
  │ Avg host payload │ JSON body size │ In-memory heap │ Safe limit  │
  ├──────────────────┼────────────────┼────────────────┼─────────────┤
  │ 2 KB             │ ~100 MB        │ ~200–400 MB    │ 512 MB–1 Gi │
  │ 5 KB             │ ~250 MB        │ ~500 MB–1 Gi   │ 1.5–2 Gi    │
  │ 10 KB            │ ~500 MB        │ ~1–2 Gi        │ 3–4 Gi      │
  └──────────────────┴────────────────┴────────────────┴─────────────┘

  The 2–4x overhead comes from Go maps/slices for passwd_file/group_file and the CallbackPayload structs.

  For 50k hosts, my recommendation is:
  ────────────────────────────────────

  resources:
    requests:
      cpu: "1000m"
      memory: "1Gi"
    limits:
      cpu: "2000m"
      memory: "2Gi"

  If your average host payload is larger than ~5 KB, raise the memory limit to 3–4 Gi.

  CPU: usually not the bottleneck
  ───────────────────────────────

  With one callback:

  1. One goroutine parses the giant JSON → short CPU spike.
  2. 10 workers then do mostly DB I/O (insert hosts, scan results, snapshots).
  3. 10 async comparison goroutines run afterwards.
  So the workload is DB-bound, not CPU-bound. Two cores are enough to keep the workers and GC busy. More replicas/cores will not make a single 50k-host callback finish faster because the 10-w
  orker pool is fixed.

  Rough ingestion time estimate
  ─────────────────────────────

  Assuming each host needs ~20–50 ms of DB work:

  50,000 hosts ÷ 10 workers × 30 ms ≈ 150 seconds

  So a 50k-host scan will take roughly 2–4 minutes to fully ingest, depending on DB latency.

  Important tuning for this pattern
  ─────────────────────────────────

  In your Deployment, set:

  env:
    - name: GOMEMLIMIT
      value: "1500MiB"   # keep GC honest, well below the 2 Gi limit
    - name: GOGC
      value: "50"        # trade a bit more CPU for lower peak RSS

  Also make sure your Postgres pod can keep up. For 50k hosts the backend will do hundreds of thousands of small inserts in a few minutes. Recommended for the DB pod:

  resources:
    requests:
      cpu: "1000m"
      memory: "2Gi"
    limits:
      cpu: "2000m"
      memory: "4Gi"

  And use fast storage (SSD-backed PVC) for PostgreSQL.

  Horizontal scaling note
  ───────────────────────

  Because the 50k hosts arrive in one callback, Kubernetes HPA will not help that single callback. It only helps if:

  • Multiple scans run at the same time
  • Many users hit the UI/detail pages while ingestion is running
  So you can start with 1 replica, or 2 replicas for HA, but don’t expect scaling to speed up one giant envelope.
